## 1. Теория

### Модульность и область видимости в JavaScript

Любой язык, рассчитанный на программы из нескольких файлов, должен решить
одну и ту же задачу: как эти файлы будут  ссылаться друг на друга и что из
написанного в одном файле остаётся его внутренним делом, а что станет
частью интерфейса, которым пользуются остальные. Решение этой задачи
называют модульностью. В JavaScript история этого решения делится на «до» и
«после» 2015 года, и прежде чем разобрать, как организована модульность на проекте,
стоит зафиксировать, как она устроена в современном JS — без этого
эталона будет непонятно, в чем проект следует канону, от чего отступает, и какими
причинами это вызвано.

Отправная точка здесь — область видимости: правило, определяющее, где имя
переменной или функции остаётся доступным. В JavaScript таких правил
исторически три, и они не равноценны.

Глобальная область видимости — самая широкая и самая опасная из трёх. В
браузере она соответствует объекту `window` (в Node.js — `global`): любое
имя, объявленное через `var` на верхнем уровне обычного `<script>`-тега,
становится свойством этого объекта. Если `util.js` объявляет
`var el = ...`, то после его загрузки существует `window.el`, видимый из
любого другого файла страницы. Удобство здесь обманчиво: два файла,
случайно объявившие одно и то же имя, тихо затирают друг друга — тот, кто
загрузился позже, побеждает без единого предупреждения. Эту область
видимости удобно представлять как общую коммунальную кухню: плита одна на
всех, и ничто не мешает соседу переставить вашу кастрюлю или просто унести её с собой.

Функциональная область видимости устроена противоположным образом: всё,
объявленное внутри функции, снаружи этой функции попросту не существует. До
появления иных механизмов это был единственный надёжный способ что-то
скрыть в JavaScript — отсюда и вырастает приём с немедленно вызываемой
функцией (IIFE), которому посвящён отдельный раздел ниже.

Блочная область видимости, появившаяся с `let` и `const` в ES2015, уже
более строга: видимость ограничена парой фигурных скобок. Она решает ряд частных
неудобств (переменная цикла больше не «утекает» за пределы `for`), но не
решает проблему «файл против файла»: `let`, объявленный на верхнем уровне
обычного `<script>`, всё так же делится между всеми скриптами страницы —
просто формально не становится свойством `window`.

Ответом на ограничения всех трёх перечисленных выше правил стали ES-модули (ESM) — штатный, не
требующий сборщика механизм модульности, встроенный в сам язык и в браузер.
Файл, подключённый как `<script type="module" src="util.js">`, получает
собственную область видимости автоматически: всё объявленное в нём по
умолчанию недостижимо снаружи, и в `window` не попадает ничего. Наружу
отдаётся только то, что явно помечено ключевым словом `export`:

```js
// util.js
const PRIVATE_DEFAULT = 120;              // снаружи недостижимо вообще никак
export function el(tag, attrs) { ... }    // часть публичного API модуля
export const MIN_W = 24;
export default el;                        // «главный» экспорт, если он единственный
```

```js
// view-table.js
import el, { MIN_W } from './util.js';           // default-экспорт + именованный
import * as Util from './util.js';                 // всё пространство имён как один объект
import { el as makeEl } from './util.js';           // импорт с переименованием
```

У этого механизма пять свойств, которых не было и не могло быть у простого
набора `<script>`-тегов.

Во-первых, порядок загрузки вычисляется автоматически: разработчик не
перечисляет файлы в правильной последовательности — браузер сам строит
граф зависимостей по инструкциям `import` и грузит/исполняет модули в
топологическом порядке. Циклические зависимости при этом не ломают всё
подряд, а обрабатываются по заранее определённым правилам.

Во-вторых, граф зависимостей статичен: прежде чем какой-либо модуль начнёт
исполняться, движок уже знает, что он импортирует и откуда (так называемая
фаза линковки, предшествующая фазе исполнения). Опечатка в имени импорта
оборачивается ошибкой немедленно, на этапе загрузки, а не `undefined`,
который тихо всплывёт часом позже, при первом обращении. То же
свойство делает возможным удаление неиспользуемого кода: сборщики умеют статически увидеть,
какие экспорты модуля фактически вообще не используются, и не включать их в итоговый
бандл, не запуская ни строчки кода.

В-третьих, каждый модуль исполняется ровно один раз, сколько бы файлов его
ни импортировали, — все получают одну и ту же, единственную копию. Это и
есть модульный синглтон; в главе 7 будет показано, как тот же эффект
воспроизводится на проекте вручную, через IIFE.

В-четвёртых, модули всегда исполняются в строгом режиме (`'use strict'`
подразумевается, объявлять его не нужно), а `this` на верхнем уровне модуля и
равен `undefined`, а не `window`.

Наконец, подключение модуля откладывает его исполнение подобно атрибуту
`defer`: парсинг HTML-документа не блокируется, а код модуля запускается
только после построения документа.

Эти пять пунктов стоит свести в одну таблицу — не для того, чтобы
противопоставить «хорошее новое» «плохому старому», а чтобы увидеть, какая
часть этой функциональности на проекте воссоздаётся вручную, а какая
сознательно остаётся за бортом:

| | Глобальный `<script>` | ES-модуль | `ds-webui` |
|---|---|---|---|
| Приватность по умолчанию | нет (всё в `window`) | да | да, через IIFE |
| Публичный API | то, что успели положить в `window` | ключевое слово `export` | запись в `window.DS_APP` |
| Порядок загрузки | задаётся руками, в HTML | вычисляется автоматически по графу | задаётся руками, в HTML |
| Пропавшая зависимость | `undefined` в рантайме | ошибка на этапе линковки | `undefined` в рантайме |
| Работает по протоколу `file://` | да | нет (см. ниже) | да |

Последняя строка этой таблицы и есть причина, по которой на проекте было принято решение использовать не ES-модули, а механизм, которому они пришли на смену.

### Почему `file://` закрывает дорогу к `import`/`export`

Ограничение, о котором говорит последняя строка таблицы, не имеет отношения
к возможностям самого языка — ES-модули прекрасно работают в любом
современном браузере. Дело в том, как браузер загружает модуль: запрос идёт
через `fetch`, а `fetch`, в свою очередь, подчиняется тем же правилам
безопасности — same-origin policy и её частичному послаблению, CORS, — что
и любой другой сетевой запрос со страницы.

Чтобы разобраться, что именно эти правила запрещают, нужно сперва точно
определить, что такое origin («источник»). Origin — это тройка из схемы,
хоста и порта, и ничего больше:

```
https://example.com:443/app/index.html
└─┬──┘   └────┬────┘ └┬┘
 схема       хост     порт        → origin: "https://example.com:443"
```

Путь (`/app/index.html`), query-строка и фрагмент адреса в это понятие не
входят. Отсюда ряд следствий, которые полезно проверить на конкретных парах
адресов: `https://example.com/a.html` и `https://example.com/deep/nested/
b.js` принадлежат одному origin, поскольку путь не учитывается; `https://
example.com` и `http://example.com` относятся к разным origin, поскольку
различается схема; `https://example.com` и `https://api.example.com` —
тоже к разным, поскольку поддомен образует отдельный хост; `https://
example.com` и `https://example.com:8443` различаются уже только портом, но
этого достаточно, чтобы считаться разными origin.

Same-origin policy — одно из фундаментальных правил безопасности веба: код,
загруженный с одного origin, по умолчанию не может прочитать ответ,
полученный с другого. Без этого правила вкладка с произвольным сайтом могла
бы обычным `fetch`-запросом вычитать содержимое вашей почты в соседней
вкладке — браузер всё равно отправил бы туда ваши собственные cookies.
Важная тонкость: запрет касается именно чтения ответа, а не самой
возможности отправить запрос, поэтому `<img src="чужой-сайт">` исправно
работает, но прочитать тело такого ответа из JavaScript нельзя.

CORS (Cross-Origin Resource Sharing) — механизм, которым сервер может
осознанно ослабить это правило для себя: в ответе на запрос он добавляет
заголовок `Access-Control-Allow-Origin: https://example.com` (либо `*`),
сообщая браузеру, что этому origin разрешено читать его ответы. Решающая
деталь здесь в том, кто выдаёт разрешение, — это делает сервер, а не
клиент. «Отключить CORS» со стороны страницы невозможно в принципе;
можно только договориться с владельцем сервера о соответствующей настройке.

Когда страница открыта по протоколу `file://` (например,
`file:///home/.../index.html`), каждый файл на диске браузер трактует как
отдельный, непрозрачный origin: у `file://a.js`, запрошенного из `file://
index.html`, с точки зрения браузера нет общего origin с запрашивающей
страницей, и запрос модуля блокируется (`Cross-Origin Request Blocked` в
консоли). Это не изъян конкретной реализации, а согласованное, одинаковое
во всех современных браузерах ограничение.

Согласно функциональным требованиям — проект без серверной части,
и обязан открываться прямо с диска, без локального
сервера: раздать коллеге рабочую копию означает отдать ему папку с файлами,
без `npm start` и без единой внешней зависимости. Поскольку `import`/
`export` в таких условиях недоступны, остаётся единственный работающий
вариант — классическая инъекция `<script src="...">` без атрибута
`type="module"`. Такие теги загружаются как обычные файлы, а не как модули,
и правилам CORS не подчиняются вовсе.

### Глобальный объект как замена механизму импорта

Отказ от `import`/`export` означает и отказ от того автоматического
механизма, которым они передают функции и переменные между файлами. Решение,
которое было реализовано на проекте — в точности то, которым весь JavaScript
пользовался до появления модулей, в эпоху jQuery-плагинов, примерно
2005–2015 годов: один общий объект в глобальной области видимости, в
который каждый файл дописывает то, что хочет сделать доступным извне, и из
которого более поздние файлы это читают.

Таких объектов на проекте два, с разделением по смыслу: `window.DS` —
пространство для данных (источники, которые подгружаются отдельными
`<script>`-тегами уже во время работы приложения, а не на старте), и
`window.DS_APP` — пространство для кода, то есть для функций каждого
модуля.

Из этой схемы прямо следует, почему порядок `<script>`-тегов в `index.html`
критичен: если `view-build.js` в момент своего исполнения обращается к
`App.el` — функции, объявленной в `util.js`, — то `util.js` обязан стоять в
документе раньше. Никакого автоматического построения графа зависимостей,
как в случае с ES-модулями, здесь нет: порядок выставляется руками и
совпадает с порядком, в котором файлы физически исполняются сверху вниз.

### IIFE и замыкания: приватность без модульной системы

Если бы каждый файл просто объявлял `var el = ...` на верхнем уровне, все
файлы делили бы одну и ту же глобальную область видимости — и имя `el` из
одного файла перетирало бы одноимённое `el` из другого ровно в духе
коммунальной кухни, описанной выше. Решение — обернуть всё содержимое файла
в немедленно вызываемое функциональное выражение, или IIFE (immediately-
invoked function expression): `(function () { ... })()`. Всё, что объявлено
внутри такой функции, остаётся её локальными переменными и не просачивается
в глобальную область; наружу публикуется только то, что явно записано в
`window.DS_APP.имя = ...` — то же разделение на приватное и публичное, какое
в модулях обеспечивает `export`, только устроенное руками, а не языком.

Этот приём напрямую связан с механизмом замыканий, и связь стоит
проговорить здесь явно. IIFE создаёт область видимости, но замыкание — это
механизм, который не позволяет этой области исчезнуть после того, как
функция уже отработала. Без замыканий сам приём IIFE был бы бессмысленен:
функция выполнилась бы и тотчас потеряла все свои переменные, и спрятать в
ней что-либо надолго было бы невозможно.

Общее определение таково: замыкание — это функция вместе с захваченной ею
областью видимости, той самой, в которой эта функция была создана. Пока на
функцию существует хотя бы одна живая ссылка, живы и все переменные,
которые она захватила, — даже если внешняя функция, объявившая эти
переменные, давно вернула управление и, казалось бы, закончила работу.

Рассмотрим этот механизм на реальном фрагменте:

```js
(function (root) {
  var DEFAULT_COL_W = 120;                 // приватная переменная IIFE
  var colWidthPx = function (state) {      // функция, созданная внутри этой области
    return ... DEFAULT_COL_W ...;          // и читающая DEFAULT_COL_W
  };
  root.DS_APP.colWidthPx = colWidthPx;     // ссылка на функцию уходит наружу, в window
})(window);
// IIFE выполнилась и завершилась. Но DEFAULT_COL_W продолжает существовать:
// замыкание внутри colWidthPx держит на неё ссылку, а сама colWidthPx -- в window.DS_APP.
```

Снаружи `DEFAULT_COL_W` недостижима в полном смысле слова: нет синтаксиса,
которым до неё можно было бы дотянуться из другого файла или консоли
разработчика. При этом переменная не перестаёт существовать — она хранит
значение и доступна единственной функции, которой это значение нужно. Это и
есть инкапсуляция в её наиболее строгом виде: не просто договорённость «не
трогать» на уровне контракта, а физическая недоступность переменной для
разработчика. В качестве контраста можно вспомнить
конвенцию `_`-префикса, которая встречается в том же проекте
(`_entityColumns`, `_swap`), — там приватность лишь обозначена именем, и
ничто не помешает вызвать `DS_APP._swap` напрямую, если функция всё же
экспортирована.

Та же механика используется и в языках, где в ней нет настоящей
необходимости. Python поддерживает замыкания, и исторически они применялись
для инкапсуляции точно таким же образом:

```python
def make_counter():
    count = 0                  # локальная переменная внешней функции
    def increment():
        nonlocal count         # явная отметка: пишем во внешнюю переменную, не создаём свою
        count += 1
        return count
    return increment           # count остаётся жива в замыкании возвращённой функции

c = make_counter()
c()   # 1
c()   # 2
# до count снаружи не добраться: c.count не существует, это не атрибут объекта
```

Различие между JavaScript и Python — в степени необходимости этого приёма. В
Python замыкания для инкапсуляции почти не требуются: у него есть
настоящая система модулей (`import` работает без сборщиков и без каких-либо
аналогов CORS) и классы, а приватность внутри них регулируется конвенцией
(`_name` как внутреннее по соглашению имя, двойное подчёркивание как
механизм name mangling — впрочем, тоже обходимый). Питонист скорее применит
замыкание ради фабричной функции, декоратора или частичного применения, чем
ради того, чтобы просто скрыть константу, — для этого достаточно поместить
её в модуль и не экспортировать.

В Rust дисциплина ещё строже: видимость имени определяется явным ключевым
словом `pub` (или его отсутствием), и компилятор не оставляет способа
обойти это решение — к системе модулей Rust мы вернёмся в посвящённом ей
разделе Rust-трека ниже. Замыкания в Rust существуют (трейты `Fn`, `FnMut`,
`FnOnce`), но роль механизма приватности им не отведена: эта роль целиком
принадлежит системе модулей языка.

JavaScript до появления ES-модулей оказался единственным из трёх
рассмотренных языков, у которого модульной системы не было вовсе — поэтому
замыкание было для него не одним из доступных инструментов инкапсуляции, а
единственным. IIFE, которую можно найти в начале каждого файла проекта,
не стилистическая причуда, а то самое решение, которое принимало
всё JavaScript-сообщество в период 2005–2015 годов, и по той же самой
причине — альтернативы просто не существовало.

Более тонкие аспекты механики замыканий — в частности, самый коварный из
них: замыкание удерживает переменную, а не её значение на момент создания —
разбираются подробно в главе 7, на живом примере пары `currentState`/
`currentDispatch` из `view-table.js`.

## 2. Разбор кода

### `index.html` — порядок тегов

```html
<script>
  window.DS = { sources: {} };
</script>
<script src="util.js"></script>
<script src="effects.js"></script>
<script src="import/vendor/xlsx.full.min.js"></script>
<script src="import/import.js"></script>
<script src="dataset.js"></script>
<script src="formula.js"></script>
<script src="entities.js"></script>
<script src="export.js"></script>
<script src="store.js"></script>
<script src="view-common.js"></script>
<script src="view-build.js"></script>
<script src="view-entities.js"></script>
<script src="view-table.js"></script>
<script src="main.js"></script>
```

Комментарий в самом файле (строки 13-21) прямо объясняет, зачем первым инлайновым
`<script>` создаётся `window.DS = { sources: {} }`: это должно существовать *до*
первого файла источника, который позже допишет туда свои данные — курица-и-яйцо
решается явной инициализацией пустого объекта раньше всех.

Обратите внимание на `import/vendor/xlsx.full.min.js` и `import/import.js` —
третий и четвёртый тег. `import/` это опциональный git submodule; если он не
инициализирован, браузер получит `404` на оба `<script src>` — и **не упадёт**:
ненайденный `<script>`-тег просто не выполняется, остальные теги документа это не
блокирует. Позже `view-build.js` перед показом кнопки «Импорт» проверяет
`window.DS_APP.importXlsx` — если его нет (оба файла не загрузились), кнопка
просто не рисуется. Это пример плавной деградации ("graceful degradation") без единого `try/catch`.

Конкретные строки: проверка — `view-build.js:162` (с поясняющим комментарием на
строке 157), сам вызов при выборе файла — `view-build.js:166`. На другом конце:
`import/import.js:222` экспортирует `importXlsx` в `window.DS_APP` (сама
функция — `import/import.js:175`), и это, как сказано в шапке того файла
(строка 10), её единственная публичная точка входа. То есть связь между двумя
репозиториями держится ровно на одном имени в одном общем объекте — ни
`import`-а, ни манифеста зависимостей, ни проверки типов: если `import.js`
переименует свой экспорт, `view-build.js` молча перестанет показывать кнопку,
и никакая сборка об этом не предупредит.

### `main.js` — структура файла

Всё содержимое — одна IIFE (строка 11: `(function () {`, закрывается на 391:
`})();`). Сразу внутри — чтение всего нужного из `App = window.DS_APP` в локальные
переменные (строки 13-31):

```js
var App = window.DS_APP;
var el = App.el, clear = App.clear, fmtDate = App.fmtDate;
var selectedNames = App.selectedNames, manifestSource = App.manifestSource,
    createStore = App.createStore, reducer = App.reducer, initialState = App.initialState,
    ...
```

Это не просто сокращение письма — это декларативный список "от чего зависит этот
файл", сосредоточенный в одном месте в начале. Прочитав только эти 19 строк,
можно понять весь граф зависимостей `main.js`, не читая остальные 11 файлов.

### Монтаж и подписка (строки 166-279)

```js
var store = createStore(reducer, initialState);
...
store.subscribe(render);
```

`createStore`/`reducer`/`initialState` пришли из `store.js` (разберём в главе
3) — здесь важно только то, что `store` это объект с `dispatch`/`getState`/
`subscribe`, и `render` подписывается на **любое** изменение состояния. Больше
про это — в главе 6 (рендер без Virtual DOM).

### Бутстрап (строки 292-389)

Три функции, три слоя:

- `bootstrapManifest(dir)` (строка 292) — грузит манифест + опциональные
  фрагменты для конкретного каталога, ничего не решает про fallback.
- `initialBoot()` (строка 315) — решает, откуда брать данные при первом запуске:
  пробует `data/`, если манифеста там нет вообще (`rawManifest === null`,
  отличие от "манифест есть, но источников в нём пусто") — пробует
  `sample-data/`.
- Главный `.then()` в конце файла (строка 334) — читает `sessionStorage`
  (`storage.get('preset')`), проверяет watchdog-флаг на случай, если прошлый
  рендер уронил вкладку (комментарий 347-356 — механизм разбирать не будем
  подробно сейчас, это скорее тема главы про производительность), и либо
  восстанавливает сохранённый пресет, либо запускает пресет по умолчанию.

Для первого прохода не нужно понимать каждую строчку watchdog-логики — важно
увидеть сам **порядок**: манифест → проверка сохранённого состояния → dispatch →
`buildDataset`. Это стандартная форма bootstrap для любого SPA, независимо от
того, есть фреймворк или нет.

## 4. Упражнения в DevTools (15-20 минут каждое)

**1.4 — ориентация в Sources.** Откройте `ds-webui/index.html` в Chrome/Firefox
через `file://`. Откройте DevTools (F12) → вкладка **Sources** → найдите дерево
файлов страницы (в Chrome — панель слева, раздел `file://`). Найдите `main.js`,
откройте его и сверьте первые 10 строк с тем, что в репозитории — убедитесь, что
это дословно тот же текст (никакой минификации/трансформации).

**1.5 — инспекция через Console.** Во вкладке **Console** наберите
`window.DS_APP` и раскройте объект. Найдите в нём `el`, `createStore`, `viewBuild`
— определите (сверяясь с `index.html`), из какого файла каждый из них пришёл.
Затем наберите `window.DS` — почему там сейчас (до выбора источников в интерфейсе)
`{ sources: {} }`, а не пусто?

**1.6 — Network, пустая сборка.** Откройте вкладку **Network**, поставьте фильтр
по типу `JS`, перезагрузите страницу (Ctrl+R). Посчитайте число запросов — должно
совпасть с числом `<script src>`-тегов в `index.html` (за вычетом двух `import/*`,
если submodule не инициализирован — у них будет статус `404`, это ожидаемо).
Откройте любой запрос и посмотрите заголовки ответа — какой `Content-Type`
присылает браузер для локального файла по `file://`?

**1.7 — Overrides, безопасный "саботаж".** Вкладка **Sources** → подраздел
**Overrides** → разрешите доступ к папке, выберите пустую временную директорию.
Откройте `index.html` в дереве файлов, найдите строку `<script src="store.js">`,
закомментируйте её прямо в DevTools (это создаёт локальную копию-переопределение,
реальный файл на диске не меняется) — перезагрузите страницу. Какую ошибку вы
теперь видите в Console? Совпадает ли она с вашим предсказанием из упражнения 1.2?
Когда закончите — отключите override (выключите переключатель в панели Overrides),
чтобы вернуть исходное поведение.
