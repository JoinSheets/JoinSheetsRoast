## 1. Теория

### Зазор между юнит-тестами и настоящим браузером

Предыдущая глава установила, почему чистые функции — самый дёшевый объект
автоматической проверки, и почему `store.js`'s редьюсеры тестируются без
единого обращения к браузеру. Но у этой дешевизны есть цена: юнит-тест
импортирует функцию напрямую через `require()`, минуя `index.html` и порядок
его `<script>`-тегов целиком, — а значит, он физически не способен заметить
целый класс ошибок, которые живут именно на границе между файлами, а не внутри
одного из них. Забытый экспорт нужной функции в объект `api`, перепутанный
порядок подключения файлов (глава 1), сломанная ленивая ссылка на
`window.DS_APP` (например, если `main.js` попытается прочитать
`App.viewBuild`, а `view-build.js` на самом деле не подключился) — ни один из
этих багов не воспроизводится при прямом `require()`, потому что все файлы в
такой схеме доступны всегда, независимо от того, в каком порядке их
действительно загрузит браузер.

Общее для всех экосистем решение этого зазора называется end-to-end- или
интеграционным тестированием через настоящую (или максимально похожую на
настоящую) среду выполнения — чаще всего это означает поднять реальный
браузер под управлением инструмента вроде Selenium или Playwright и
прогнать через него пользовательский сценарий целиком. `ds-webui` идёт
другим путём, тем же, что и выбор `node:test` вместо `jest` в прошлой главе:
не поднимать внешний процесс и не тащить зависимость, а воссоздать ровно тот
минимум поведения браузера, который нужен для одной конкретной проверки —
что бутстрап приложения, с настоящим порядком файлов и настоящим кодом,
реально срабатывает от начала до конца.

### `vm`: песочница вместо браузера

Способ добиться этого без браузера даёт встроенный, редко всплывающий в
обычном веб-разработческом коде модуль Node.js — `vm`. `vm.createContext(obj)`
создаёт изолированное пространство выполнения («песочницу»), где `obj`
становится глобальным объектом этой песочницы — ролью, которую в настоящем
браузере играет `window`. `vm.runInContext(sourceCode, ctx)` выполняет текст
JS-кода — не функцию, а буквально строку исходного текста — внутри этой
песочницы, как если бы это был очередной `<script>`-тег страницы. Это и есть
необходимый инструмент: не эмуляция DOM, а именно повторение того, как
браузер физически исполняет последовательность `<script src="...">`.

### jsdom и сознательный отказ от него

Самый частый выбор для тестирования браузерного кода в Node — `jsdom`,
полноценная (хоть и неполная) реализация DOM на чистом JavaScript, вокруг
которой построены тестовые окружения многих крупных фреймворков. `ds-webui`
обходится без неё по той же причине, по которой избегает любых других
зависимостей: `makeNode()` реализует только то, что реально требуется для
одного прохода бутстрапа — `appendChild`/`removeChild`/`setAttribute`/
`classList`/минимальный `dataset`, — а не DOM целиком. Это классическое
решение в пользу fake, а не полноценной реализации (терминология из прошлой
главы): дешевле в поддержке, но и честно, явно ограничено по охвату.
Комментарий самого файла прямо предупреждает: «не считать это заменой
настоящего браузера» — если добавить функциональность, которая трогает
`querySelector` с реальной выборкой или `getBoundingClientRect`, этот стаб
её не проверит (он либо не реализует эти методы вовсе, либо реализует
заглушками, возвращающими пустоту).

## 2. Разбор кода

### `makeNode` — минимальный фейковый DOM-узел

```js
function makeNode(tag) {
  const node = {
    tagName: tag, attrs: {}, children: [], parentNode: null, ...
    setAttribute(k, v) {
      this.attrs[k] = String(v);
      if (k === 'id') idRegistry[v] = this;
    },
    appendChild(child) { child.parentNode = this; this.children.push(child); return child; },
    ...
  };
  node.classList = { _set: new Set(), add(c){...}, remove(c){...}, toggle(c, force){...}, contains(c){...} };
  return node;
}
```

Простой объект, не класс — каждый вызов `makeNode('div')` создаёт новый
объект со своими методами-замыканиями (чуть расточительно по памяти по
сравнению с прототипом/классом, но для теста — не важно, узлов десятки, не
миллионы). `setAttribute('id', v)` специально регистрирует узел в глобальном
`idRegistry` — имитация того, что `document.getElementById(id)` в настоящем
браузере просто "находит" элемент по дереву; тут проще сразу завести реестр.

### Перехват `<script src>` — самая хитрая часть файла

```js
function wireScriptLoading(node) {
  const origAppend = node.appendChild.bind(node);
  node.appendChild = function (child) {
    const r = origAppend(child);
    if (child.tagName === 'script' && child.src) {
      const src = loadFileSync(child.src);
      if (src == null) { if (child.onerror) child.onerror(); }
      else { vm.runInContext(src, vmContext, { filename: child.src }); if (child.onload) child.onload(); }
    }
    return r;
  };
}
```

Это **monkey-patching**: берём оригинальный метод (`origAppend`), сохраняем
ссылку на него, затем ЗАМЕНЯЕМ `node.appendChild` на новую функцию, которая
сначала вызывает оригинал, а потом добавляет своё поведение. Комментарий
файла (строки 152-155) объясняет важную деталь: проверка именно `child.src`
(JS-свойство, IDL-property), а не `child.getAttribute('src')` — потому что
реальный код `ds-webui`, динамически догружающий файлы источников
(`effects.js::loadSourceScript`), ставит `.src` как свойство, а не через
`setAttribute`. Это прямое применение урока главы 2 (атрибут vs свойство) —
стаб обязан проверять именно то поле, которое реальный код реально
использует, иначе тест будет проверять не настоящее поведение, а
придуманное.

### `--simulate-crash` — тест ветки восстановления после сбоя

```js
if (SIMULATE_CRASH) {
  sessionStorageStore['ds-webui:renderWatchdog'] = 'true';
  sessionStorageStore['ds-webui:preset'] = JSON.stringify(POISONED_PRESET);
}
```

Это пример **fixture** (заранее подготовленных входных данных для
конкретного сценария) — имитирует вкладку, у которой прошлый `render()` не
дошёл до подтверждённого кадра (напоминание: `main.js`'s watchdog-механизм,
глава 1 кратко упоминала, подробнее — глава 9). Тест в этом режиме проверяет
не "всё хорошо", а конкретную ветку восстановления: пустой пресет вместо
убийственного, сохранённый пресет не затёрт.

### Финальные проверки — `expectedExports`

```js
const expectedExports = [
  'el', 'joinSources', 'matchCondition', 'parseNum', 'parseDate', 'toCsv',
  'createStore', 'reducer', 'normalizePreset', 'opSelect', 'viewNav', 'viewBuild',
  'viewTableShell', 'renderGrid', 'store', 'buildDataset', 'exportXls', 'exportCsv'
];
const missing = expectedExports.filter((k) => typeof DS_APP[k] === 'undefined');
assert.deepEqual(missing, [], ...);
```

Это именно тот список, из которого в прошлой сессии убрали `'pipe'` (когда
саму функцию удалили из `util.js` как мёртвый код) — если бы список не
обновили, тест бы упал с "отсутствует экспорт: pipe", хотя на самом деле
отсутствие `pipe` — ожидаемое, правильное состояние после рефакторинга.
Урок: такие списки-белые-списки нужно обновлять синхронно с самим кодом, и
тест на них — не "истина в вакууме", а снимок ожиданий на момент написания.

## 3. Упражнения (бумага)

**5.1** `srcScripts` (строка 204) извлекается регулярным выражением прямо из
текста `index.html`, а не хранится отдельным захардкоженным списком файлов в
самом тесте. Почему это важнее, чем кажется — что могло бы произойти, если бы
список дублировался (кто-то добавил новый `<script>` в `index.html`, но забыл
обновить "параллельный" список в тесте)?

**5.2** Строка `vm.runInContext(inlineScript[2], vmContext, ...)` выполняет
инлайновый `<script>` (`window.DS = {sources: {}};`) из `index.html` отдельно,
ПЕРЕД внешними `<script src>`. Почему порядок важен — что случилось бы, если
бы инлайн-скрипт выполнился ПОСЛЕ, скажем, `effects.js::loadSourceScript`
(гипотетически, если бы она вызывалась раньше в бутстрапе)?

**5.3** Комментарий строки 226-229 объясняет, почему тест не использует
`assert.deepEqual(state.preset, {})`, а вместо этого
`Object.keys(state.preset.query.sources).length === 0`. Своими словами
объясните проблему "cross-realm" прототипов — почему объект, созданный
ВНУТРИ `vm`-контекста, и `{}`, написанный в самом тестовом файле, технически
разные "виды" объектов для строгого сравнения.

непокрытые (красные) строки — код, который вы не вызвали в этом конкретном

`view-build.js` ветку, связанную с кнопкой «Импорт» (`window.DS_APP.
importXlsx`, глава 1) — покрыта ли она, если `import/`-submodule не
инициализирован?

**5.5 — воссоздать "забытый экспорт" своими руками.** Через Sources →
Overrides (глава 1) временно закомментируйте в `util.js` строку экспорта

ошибку и должен бы поймать `expectedExports`-список смоук-теста.

## 5. Rust-трек

`cargo test` умеет интеграционные тесты в отдельной директории `tests/` —
концептуально похоже на разделение "unit-тесты внутри модуля" / "смоук-тест
снаружи, через публичный API" в `ds-webui` (юнит — `tests/*.test.js` напрямую
импортируют функции; смоук — `tests/smoke/dom-smoke.js` запускает всё "снаружи",
как пользователь). В Rust это ещё более жёстко разделено физически: файлы в
`tests/` каталоге видят ТОЛЬКО публичный (`pub`) API вашего крейта — не
внутренние детали, даже если бы захотели. Задание: для вашей Rust-версии
`sort_reducer` (глава 3) создайте отдельный файл `tests/integration.rs` (не
`#[cfg(test)] mod tests` внутри того же файла, а отдельный файл верхнего
уровня) — убедитесь, что `cargo test` подхватывает оба набора тестов
отдельно, и обратите внимание, что `tests/integration.rs` обязан явно
`use your_crate::...` — не видит приватные функции напрямую, если они не
`pub`.
