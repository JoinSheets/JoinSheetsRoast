## 1. Теория

### WebAssembly как ещё одна виртуальная машина в браузере

WebAssembly — не «JS, но компилируемый», а отдельный, компактный,
типизированный бинарный формат байт-кода, который браузер выполняет в
собственной песочнице-VM, параллельно с обычным JS-движком, а не вместо
него. Код для WASM обычно пишут на языке, для которого существует
компилятор с таргетом WASM — Rust, C/C++, Go и другие, — и получившийся
модуль совсем не «подмножество JS»: у него нет своего DOM, нет своего
`document`, нет сборщика мусора в привычном смысле. Это низкоуровневая
виртуальная машина с линейной памятью — одним большим массивом байт — и
набором экспортируемых функций, ничего больше. `wasm-bindgen` — инструмент,
генерирующий «клей»: JS-файл, который умеет вызывать функции
скомпилированного `.wasm`-модуля и передавать значения в обе стороны —
числа почти бесплатно, напрямую, а строки и объекты копируются через
линейную память WASM-модуля, и это копирование не бесплатно.

### Граница между языками как общая, а не специфичная для WASM проблема

Задача «передать управление и данные из одной среды выполнения в другую,
с разными моделями памяти» возникает не только на стыке JS и WASM — это
частный случай значительно более общей темы, десятилетиями известной под
именем FFI, foreign function interface. Python-овский код, вызывающий
библиотеку на C через `ctypes` или `cffi`; Java, зовущая native-код через
JNI (Java Native Interface); Node.js, подключающая C++-надстройки через
N-API — во всех этих случаях каждое пересечение границы стоит заметно
дороже обычного вызова функции внутри одной среды: нужно сконвертировать
представление данных, скопировать память, иногда — синхронизировать
сборщики мусора двух разных runtime. Общий урок инженерной практики здесь
один и тот же, независимо от конкретной пары языков: пересекать границу
нужно редко, но с большими порциями данных, а не часто и мелкими
порциями — цена одного пересечения почти постоянна, и чем больше полезной
работы удаётся сделать за одно пересечение, тем меньше эта цена в
пересчёте на единицу результата.

Этот общий урок напрямую определяет, как нужно переносить `formula.js` на
Rust+WASM, а не как самая частая и самая естественная на первый взгляд
ошибка подхода «перепишем на Rust+WASM, чтобы стало быстрее» — перенести
вычисление в точности так, как оно сейчас вызывается в JS, не задумываясь о
границе между средами. `formula.js::evaluate(ast, ctx)` в реальном
конвейере `ds-webui` (`entities.js::resolveCell`) вызывается один раз на
каждую ячейку каждой строки с формулой — для таблицы в 10000 строк и 3
формульных столбца это 30000 отдельных вызовов. Если наивно перенести
каждый такой вызов через границу JS→WASM по отдельности (передать формулу
и контекст, получить строку результата) — накладные расходы на 30000
отдельных пересечений границы вполне способны съесть весь выигрыш от более
быстрого вычисления внутри. Правильный перенос обязан пересекать границу
реже, но с большими порциями данных сразу — например, передать формулу и
всю колонку строк разом, посчитать все 10000 значений внутри Rust за один
вызов и вернуть массив результатов одним махом. Это не нюанс для
продвинутых, а решение, определяющее успех всего капстоуна: без него есть
реальный риск получить честный, но обескураживающий результат «WASM-версия
оказалась медленнее» — сам по себе ценный вывод, а не провал, но
избегаемый, если граница спроектирована правильно с самого начала.

### Zero-build как инвариант, который капстоун обязан сохранить

Через всю программу курса проходит одно и то же требование к `ds-webui`:
никаких внешних зависимостей, никакой сборки, никакой установки — проект
должен оставаться статичным набором файлов, без единой строки серверного
кода, и открываться прямо с диска. Любая правка, предлагаемая этой главой,
обязана сохранить это требование в силе, а не создать для него частное
исключение «для производительности».

Перенос части кода на Rust и компиляция его в WASM на первый взгляд похожи
на нарушение: Rust ведь нужно компилировать, а на машине конечного
пользователя никакого компилятора нет и не предполагается. Противоречия
здесь всё же нет, потому что компилировать `.wasm`-модуль обязан
разработчик — один раз, заранее, у себя, — а не пользователь при каждом
запуске: `wasm-pack build` превращает Rust-код в пару файлов (`.wasm` и
JS-файл с «клеем»), и оба коммитятся в репозиторий как готовые, неизменные
бинарные артефакты — ровно тем же способом, каким в проект уже подключена
`import/vendor/xlsx.full.min.js`, сторонняя библиотека, тоже собранная
заранее кем-то другим. Пользователь `ds-webui` не запускает ни `cargo`,
ни `wasm-pack` — он получает ещё один `<script src="...">`, подключаемый
и загружаемый ровно так же, как любой другой файл проекта, и ничем для
него не отличимый.

WASM-модуль, таким образом, не исключение из правила «никаких внешних
зависимостей», а точечный, статичный артефакт — он решает узкую задачу
производительности одной конкретной функции и не меняет ничего в том, как
проект распространяется и запускается. Именно с этим ограничением в голове
стоит проектировать перенос — план которого описан ниже, в разделе
«План переноса».

### Шаг 10.2 — AST и парсер

`formula.js`'s AST-узлы (`{type:'binop',op,left,right}`, `{type:'if',cond,
then,else}`, ...) — тегированные объекты, то, что в Rust выражается `enum`
естественно:

```rust
enum Ast {
    Num(f64),
    Str(String),
    Raw(String),                      // [Источник.Поле]
    Var(String),                      // буква A, B, ...
    Neg(Box<Ast>),
    BinOp { op: char, left: Box<Ast>, right: Box<Ast> },
    Cmp { op: String, left: Box<Ast>, right: Box<Ast> },
    If { cond: Box<Ast>, then_: Box<Ast>, else_: Box<Ast> },
    Call { name: String, args: Vec<Ast> },
}
```

(`Box<Ast>` — необходим, потому что `Ast` рекурсивно содержит сам себя;
Rust обязан знать размер типа заранее, а рекурсивный `enum` без `Box` имел
бы потенциально бесконечный размер — ещё один урок "что JS делает неявно,
Rust требует явно".) Портируйте `parsePrimary` → `parseTernary` (рекурсивный
спуск, формула.js строки 199-291) почти 1:1 — каждая JS-функция становится
Rust-функцией, `fail(msg, tok)` (throw) становится `return Err(...)`.
Снова — мигрируйте побольше тестов из `tests/formula.test.js` на корректные
разборы (`IF(A>0, "да", "нет")`, вложенные скобки, функции) как `cargo test`.

### Шаг 10.3 — вычислитель

`evaluate(ast, ctx)` (строки 313-348) — рекурсивный обход `enum Ast` через
`match` — должен ощущаться естественнее, чем JS-`switch (node.type)`,
именно потому что каждый `Ast`-вариант уже несёт свои поля типизированно
(не нужно `node.left`/`node.right` с риском опечатки в имени поля — Rust не
скомпилирует код, если вы перепутаете имя поля или забудете один из
вариантов `enum` в `match`).

### Шаг 10.5 (стретч) — реальная интеграция в `ds-webui`

Повторите паттерн `import/` (опциональный submodule/vendored-файлы,
`window.DS_APP.importXlsx`-проверка перед использованием, глава 1): добавьте
`<script src="wasm/your_crate.js">` в `index.html` (после `formula.js`, перед
`entities.js`, которая его вызывает), с проверкой наличия перед
использованием и падением обратно на существующий `formula.js::evaluate`,
если WASM-файл не загрузился (`404`, submodule не инициализирован — тот же
паттерн graceful degradation).

## 3. Замеры — используем методологию главы 9

Повторите упражнение 9.4 (Performance panel, запись, Bottom-Up) ДВАЖДЫ: один
раз на чистой JS-версии (`formula.js::evaluate`, вызываемой построчно, как
сейчас), один раз — на вашей WASM-версии (вызываемой пачкой, как в шаге
10.4), на одном и том же датасете с достаточным количеством формульных
строк, чтобы разница была измеримой (не 10 строк — нужны тысячи). Запишите
оба числа Self Time из Bottom-Up. Любой результат — честный и ценный: и
"быстрее в N раз", и "практически без разницы", и даже "медленнее из-за
накладных расходов на сериализацию JSON через границу" (в этом случае —
следующий естественный вопрос для самостоятельного исследования: что если
передавать не JSON-строку, а типизированный `JsValue` через
`serde-wasm-bindgen`, минуя парсинг JSON-текста вовсе?).

## 4. DevTools (если дойдёте)

**Memory panel** — после загрузки WASM-модуля, Sources → найдите вкладку с
WASM-модулем в дереве файлов (Chrome умеет показывать WASM с

даже поставить брейкпоинт внутри Rust-кода, если `wasm-pack build --dev`

пункт — WASM-дебаггинг в DevTools всё ещё менее зрелый, чем для JS, не
расстраивайтесь, если что-то не заведётся гладко с первого раза.
