## 1. Теория

### Зачем нужны автоматические тесты

Пока программа маленькая, её поведение можно проверить вручную:
запустить, кликнуть, посмотреть на результат. По мере роста это перестаёт
работать — число возможных сочетаний состояния растёт быстрее, чем способность
удержать их все в голове, а любое изменение в одном месте способно незаметно
сломать поведение в другом, никак с ним на первый взгляд не связанном.
Автоматический тест — это зафиксированная, повторяемая проверка одного такого
сочетания: написанная один раз, она выполняется за миллисекунды сколько угодно
раз подряд и сообщает о регрессии в момент, когда её внёс сам разработчик, а
не когда её случайно обнаружит пользователь.

### Пирамида тестов

Не все автоматические проверки одинаковы по стоимости и по тому, что именно
они покрывают. Майк Кон предложил в середине 2000-х представлять их как
пирамиду: в основании — многочисленные, быстрые, узкие unit-тесты (одна
функция, без браузера, без сети, без файловой системы); на вершине —
немногочисленные, медленные, широкие end-to-end-тесты (всё приложение целиком,
через настоящий браузер); между ними — интеграционные тесты (несколько
модулей вместе, но ещё не всё приложение). Форма пирамиды говорит о том, что основная масса проверок должна приходиться на
узкий и быстрый нижний слой, а немногочисленные широкие тесты наверху служат
страховкой, а не основным инструментом.

В `ds-webui` эта форма прослеживается прямо в структуре каталога `tests/`.
`tests/preset.test.js`, `tests/entities.test.js`, `tests/formula.test.js`,
`tests/dataset.test.js` — нижний, самый многочисленный слой: чистые функции
модулей (`normalizePreset`, `reducer`, `parse`/`evaluate` формул), вызванные
напрямую из Node, без единого обращения к `document`/`window`. Верхний слой —
тема следующей главы: `tests/smoke/dom-smoke.js` проверяет, что приложение в
целом хотя бы запускается и основной путь работает, не вдаваясь в детали
каждой отдельной функции. Отдельного, формально выделенного интеграционного
слоя между ними в проекте нет, но часть тестов `preset.test.js` фактически
играет эту роль — тест `reducer: preset/toggleSource создаёт связку`, например,
трогает сразу несколько случаев `store.js` (нормализацию и конкретный `case`
редьюсера), а не одну изолированную функцию.

### Что делает функцию легко тестируемой

Функциональное программирование давно формализовало понятие, которое
напрямую отвечает на вопрос, что превращает код в лёгкую или трудную цель для
автоматической проверки, — референциальную прозрачность: выражение
прозрачно, если его можно без изменения смысла программы заменить его
результатом, а это возможно ровно тогда, когда функция, его вычисляющая,
при одинаковом входе всегда даёт одинаковый выход и не производит побочных
эффектов. Чистая функция не производит операции ввода-вывода — не читает `Date.now()`, не трогает DOM, не отправляет запрос.
Такую функцию тестировать дёшево: тест просто сравнивает вход с ожидаемым
выходом, не заботясь ни о каком скрытом состоянии снаружи.

Редьюсеры `store.js` — редкий пример кода, достигающего этого свойства не
частично, а полностью, что мы уже видели в прошлой главе: `reducer(state,
action)` детерминирован, не мутирует аргументы и не обращается ни к чему
внешнему. Контраст здесь нагляден: `view-table.js::renderGrid` практически
невозможно юнит-тестировать в том виде, в каком она написана — ей нужен
`document`, она читает модульные переменные (`currentState`, глава 7) и
создаёт настоящие DOM-узлы. Именно из этого контраста и вырастает нужда в
смоук-тестах и в фейковом DOM, которым посвящена следующая глава.

### Сравнение значений: равенство и структурное равенство

Почти все системы тестирования — независимо от языка — различают два разных
вопроса: «это тот же самый объект?» и «эти два значения выглядят одинаково по
содержимому?». В `node:assert` это `assert.equal` (сравнение, близкое к `==`,
корректное для примитивов) против `assert.deepEqual` (рекурсивное сравнение
структуры объектов и массивов, а не ссылок на них): `assert.deepEqual({x:
1}, {x: 1})` проходит, потому что форма одинакова, хотя это два разных
объекта в памяти, а `assert.equal({x: 1}, {x: 1})` падает, потому что `==`
для объектов сравнивает именно ссылку. Та же пара понятий встречается и в
других экосистемах под другими именами — `toBe`/`toEqual` в Jest,
`assertEqual` в Python-овском `unittest` (там сравнение для встроенных
контейнеров и так структурное), `assert_eq!` в Rust (структурное сравнение,
если тип реализует `PartialEq`, обычно через `#[derive(PartialEq)]`).
`ds-webui`'s тесты используют не просторечный `node:assert`, а его строгий
вариант, `node:assert/strict` (`const assert = require('node:assert/strict')`
в `preset.test.js`) — он заменяет `==`/`deepEqual` на `===`/`deepStrictEqual`,
а последний вдобавок сравнивает прототипы сравниваемых объектов, не только
их поля. Это отличие всплывёт не абстрактно, а на конкретном баге — в
следующей главе, где оно разделяет объекты из разных VM-контекстов.

### Arrange / Act / Assert

Любой модульный тест, в какой бы системе он ни был написан, обычно сводится
к трём шагам: подготовить исходные данные (Arrange), выполнить проверяемое
действие (Act), сравнить результат с ожидаемым (Assert). Приём не
специфичен для JavaScript — та же трёхчастная форма узнаётся в тестах на
Python, Rust или Java, — но её стоит явно держать в голове при чтении
любого теста `ds-webui`:

```js
test('normalizePreset: description сохраняется как есть, если задан строкой', () => {
  const p = App.normalizePreset({ description: 'Отчёт по клиентам за январь' }); // Act (на готовом Arrange — входные данные прямо в вызове)
  assert.equal(p.description, 'Отчёт по клиентам за январь');                    // Assert
});
```

Здесь Arrange тривиален — входной объект записан прямо в строке вызова. В
более сложных тестах (например, в тесте `reducer: preset/toggleSource`,
строки 85-90) Arrange превращается в отдельный, предшествующий шаг: нужно
собрать `state` с подходящим `manifest`/`preset`, прежде чем вызывать само
действие, которое проверяет тест.

### Тестовые двойники

Не каждую зависимость тестируемого кода удобно или нужно вызывать по-настоящему
— внешний API, таймер, браузерный DOM. Мартин Фаулер систематизировал
сложившийся в индустрии словарь для замен таких зависимостей под общим
термином test double (по аналогии с дублем актёра в кино), разделив его на
четыре разные роли, которые легко спутать между собой, но которые решают
разные задачи: **stub** — заглушка, просто возвращающая фиксированное
значение, без проверки, что её вообще вызвали; **mock** — заглушка, которая
вдобавок проверяет, что её вызвали ожидаемым образом (с нужными аргументами,
нужное число раз); **fake** — работающая, но упрощённая реализация настоящей
зависимости, не просто «верни 42», а реальная, хотя и облегчённая логика;
**spy** — обёртка вокруг настоящей функции, которая запоминает, как её
вызывали, но не меняет её поведения. В следующей главе понадобится именно
fake: `makeNode()` внутри `dom-smoke.js` — не jsdom (полноценная реализация
DOM), а минимальный, но по-настоящему работающий суррогат (`appendChild`
реально складывает детей в массив, `setAttribute` реально что-то запоминает),
собранный ровно под те нужды, которые требует бутстрап `ds-webui`, и не более
того.

## 2. Разбор кода

```js
const test = require('node:test');
const assert = require('node:assert/strict');
const App = require('../store.js');

test('normalizePreset: пустой объект -> валидная дефолтная форма', () => {
  const p = App.normalizePreset({});
  assert.deepEqual(p.query.sources, {});
  assert.deepEqual(p.view.entities, []);
  ...
});
```

`node:test` — встроенный в сам Node.js тест-раннер (с версии 18, стабилен с 20)
— никакой npm-зависимости (`jest`/`mocha`/`vitest`) не требуется, что прямо
совпадает с философией проекта "ничего не устанавливать". `require('../
store.js')` — работает потому, что сам `store.js` написан с двойным интерфейсом
(см. шапку файла, строки 8-16): если есть `module.exports` (значит, мы в Node) —
экспортировать как CommonJS-модуль; если нет (мы в браузере) — писать в
`window.DS_APP`. Один и тот же файл обслуживает оба мира без дублирования кода.

Обратите внимание на тест миграции (строка 45-48):
```js
test('normalizePreset: мигрирует старое view.column_filters в view.conditions', () => {
  const p = App.normalizePreset({ view: { column_filters: { Foo: 'bar' } } });
  assert.deepEqual(p.view.conditions, [{ field: 'Foo', op: 'contains', value: 'bar' }]);
});
```
Это тест "обратной совместимости" — не описывает текущую нормальную форму
данных, а описывает, что СТАРЫЙ формат (который, возможно, лежит в каких-то
сохранённых пресетах пользователей) по-прежнему корректно читается. Такой
тест — живая документация истории формата: удали его — рискуешь незаметно
сломать совместимость при следующей правке `normalizeConditions`.

## 4. DevTools / практика без Node

Если на рабочем компьютере нет возможности запустить `node --test` (нет
установленного Node.js) — у `ds-webui`, открытого в браузере, уже есть ЖИВОЙ
`window.DS_APP.reducer` и `window.DS_APP.store` прямо в Console. Можно
"потестировать руками", даже не трогая файловую систему:

**4.4 — редьюсер через Console как мини-тест.** Откройте `ds-webui` в браузере.
В Console выполните:
```js
var before = DS_APP.initialState;
var after = DS_APP.reducer(before, {type: 'table/toggleHideEmpty'});
after.hideEmpty       // ожидаете true
after === before      // ожидаете false — новый объект
before.hideEmpty      // ожидаете false — исходный не тронут
```
Это ручная, одноразовая имитация того же теста, который вы написали на бумаге
в 4.1 — без единого файла, без `npm`, прямо в вкладке браузера на 15-минутном
перерыве.

**4.5 — сравнение `assert.equal`/`deepEqual` своими глазами.** В той же
Console:
```js
var a = DS_APP.normalizePreset({});
var b = DS_APP.normalizePreset({});
a === b                                 // false — разные вызовы, разные объекты
JSON.stringify(a) === JSON.stringify(b) // true — "бедный" аналог deepEqual
```
`JSON.stringify`-сравнение — грубая, но рабочая на перерыве имитация
`deepEqual` без библиотеки assert (ограничение: не различает `undefined`-поля,
не сравнивает порядок ключей надёжно для всех случаев — не используйте это в
реальном коде, только для разового ручного прощупывания в консоли).

Если Node.js на рабочем компьютере всё же есть (просто нет IDE/прав на
установку пакетов) — выполните 4.1 по-настоящему: создайте файл, впишите тест,
`node --test tests/your-file.test.js`. На домашнем компьютере (там же, где
Rust) — это будет штатно работать в полном объёме.

## 5. Rust-трек

Контраст философий: в Rust тестирование — часть самого языка/`cargo`, не
отдельный пакет. `#[test]` над функцией + `cargo test` — без какого-либо
отдельного раннера, похожего на `node:test`, но роль та же: встроено,
ничего ставить не нужно сверх самого тулчейна.

```rust
fn toggle_hide_empty(hide_empty: bool) -> bool { !hide_empty }

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn toggles_from_false_to_true() {
        assert_eq!(toggle_hide_empty(false), true);
    }
}
```
Задание: напишите так же тест для вашей Rust-версии `sort_reducer` из главы 3
(`SortAdd`/`SortRemove`) — покройте оба случая, запустите `cargo test` (дома).
Обратите внимание на `assert_eq!` — тоже делает структурное сравнение (как
`deepEqual`), не ссылочное — для `Vec`/`struct`, если они реализуют `PartialEq`
(обычно через `#[derive(PartialEq)]`).
