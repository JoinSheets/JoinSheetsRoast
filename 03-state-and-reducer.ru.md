## 1. Теория

### Проблема, которую решает единый источник истины

Любое приложение с интерфейсом сложнее пары статичных экранов сталкивается с
одним и тем же вопросом: где хранится состояние (что выбрано, что открыто,
что введено) и кто имеет право его менять. В приложениях, написанных без
особой дисциплины, ответ обычно размазан по всему коду — состояние лежит в
десятках независимых переменных, DOM-атрибутов и замыканий, и любой
обработчик события может поменять любую его часть напрямую. Это работает, пока
взаимодействий немного; но по мере роста приложения отладка превращается в
расследование: баг воспроизводится, но чтобы понять, что именно и где
изменило состояние, приходится ставить точки останова во всех
местах, которые теоретически могли на него повлиять.

Архитектура Flux, представленная Facebook в 2014 году для собственных нужд
(на тот момент — для раннего React), предложила простой выход: сделать
изменение состояния возможным только через один узкий канал. Все события
интерфейса превращаются в **действия** — простые, самодостаточные описания
того, что произошло (`{type: 'строка', ...полезная нагрузка}`); единственная
функция — **хранилище** — получает такие действия одно за другим и решает,
как каждое из них меняет единое, общее состояние приложения. Этот же принцип,
независимо и почти одновременно, был доведён до предельно чистой формы в
архитектуре Elm (The Elm Architecture: Model, Update, View) — языка, в
котором подобная схема вообще единственная, встроенная в сам язык, а не
библиотека поверх него. Redux, написанный в 2015 году как попытка применить
идеи именно Elm к React-экосистеме, свёл всё это к трём формулировкам,
которые с тех пор почти повсеместно стали стандартом индустрии: состояние приложения
целиком описывается одним объектом; единственный способ его изменить — отправить
действие; и отвечает за превращение действия в новое состояние чистая
функция, называемая редьюсером, — `(state, action) => newState`, не трогающая
то состояние, которое получила на вход, а строящая новое.

`ds-webui` реализует этот паттерн не библиотекой, а напрямую — несколькими
десятками строк в `store.js`, без единой внешней зависимости (та же причина,
по которой `el()` в прошлой главе написан вручную, а не взят готовым). Любая
часть интерфейса, которой нужно узнать об изменении состояния, подписывается
на уведомления через `subscribe` — к этому механизму мы ещё вернёмся ниже.

### `createStore`: наблюдатель в чистом виде

Механизм «подписаться на изменения и быть уведомлённым, когда они случаются»
старше самого Redux и даже самого веба — это классический паттерн Observer
(он же publish/subscribe), десятилетиями применяющийся в самых разных GUI-
тулкитах и событийных системах, от слушателей в Java Swing до `EventEmitter`
в Node.js. `createStore` реализует его в предельно компактной форме:

```js
var createStore = function (reducer, initial) {
  var state = initial;
  var listeners = new Set();
  return {
    getState: function () { return state; },
    dispatch: function (action) {
      state = reducer(state, action);
      listeners.forEach(function (l) { l(state, action); });
    },
    subscribe: function (l) { listeners.add(l); return function () { listeners.delete(l); }; }
  };
};
```

`state` — переменная, захваченная замыканием (глава 7 разберёт этот механизм
подробнее) внутри `createStore`, недостижимая снаружи иначе как через
`getState()`. `dispatch` — единственное место во всём приложении, которое эту
переменную меняет, и ровно это и есть тот «один узкий канал», о котором
говорит Flux. `subscribe` возвращает функцию отписки — замыкание над
конкретным слушателем `l` и общим множеством `listeners` — ровно двенадцать
строк, и ни единой внешней библиотеки для паттерна, который в Redux занимает
отдельный npm-пакет.

### Иммутабельность как инструмент, а не стилевое предпочтение

Требование «редьюсер не мутирует старое состояние, а строит новое» на первый
взгляд похоже на стилистическую рекомендацию, но у него есть конкретное,
измеримое следствие: если новое состояние гарантированно оказывается новым
объектом при любом реальном изменении, то проверка «что-то поменялось?»
сводится к одному сравнению по ссылке (`oldState === newState`) — без
необходимости рекурсивно обходить всё дерево состояния и сравнивать его
содержимое поле за полем. Тот же трюк, в точности на той же гарантии, лежит
в основе `React.memo`/`PureComponent` — они решают, перерисовывать ли
компонент, поверхностным сравнением пропсов по ссылке, а не глубоким их
сравнением, и работают корректно ровно тогда, когда состояние, из которого
эти пропсы вычислены, тоже никогда не мутируется на месте.

В `ds-webui` эта же гарантия используется не один раз, а дважды, в двух не
связанных друг с другом местах: внутри самого `reducer()`, для диспетчеризации
по доменам (ниже в этой главе), и в `main.js::render()`, где сравнение
`state.dataset !== lastDataset` решает, нужно ли пересобирать оболочку
страницы целиком (разберём подробно в главе 6). Это не совпадение, а прямое
следствие одного и того же инварианта, который `store.js` поддерживает
централизованно: раз каждый редьюсер обязан возвращать новый объект при
любом реальном изменении, этим инвариантом может безопасно пользоваться
любой код, которому состояние только читается.

### Композиция редьюсеров: альтернатива `combineReducers`

Классический Redux обычно собирает большой редьюсер из маленьких через
`combineReducers({a: reducerA, b: reducerB})` — каждый под-редьюсер отвечает
за свой, заранее известный ключ верхнего состояния (`state.a`, `state.b`),
и вызываются они все сразу, при каждом действии.

`ds-webui` устроен иначе: ни один из восьми доменных редьюсеров (`preset/*`,
`group/*`, `sort/*` и так далее) не владеет отдельным ключом — все они читают
и пишут один и тот же, общий плоский `state`. Закреплённых ключей за каждым
доменом здесь попросту нет, поэтому вызываются они по очереди, и
диспетчеризация решается тем же инвариантом, что описан выше: если домен
вернул новый объект (`!== state`), значит, он распознал переданное действие
и результат можно возвращать сразу, не пробуя остальные; если домен вернул
тот же `state`, значит, сработал его `default`, и нужно попробовать
следующий. Это надёжно ровно потому, что ни один `case` во всём файле не
возвращает `state` «как есть» для распознанного действия — всегда
`Object.assign({}, state, ...)` или `setIn(state, ...)`, что гарантирует
новую ссылку.

## 2. Разбор кода

### Пример: один `case` целиком

```js
case 'preset/toggleSource': {
  var sources = state.preset.query.sources;
  var next;
  if (sources[a.name]) {
    next = omit(sources, a.name);
  } else {
    var ms = manifestSource(state, a.name);
    next = Object.assign({}, sources);
    next[a.name] = { labels: ms ? [ms.key] : null };
  }
  var withSources = setIn(state, ['preset', 'query', 'sources'], next);
  return setIn(withSources, ['preset', 'view', 'joins'],
    reconcileJoins(Object.keys(next), state.preset.view.joins));
}
```

Логика: если источник `a.name` уже выбран — убрать его (`omit`); если нет —
добавить с единственным дефолтным полем (ключом JOIN). Дальше — пересчитать
связки (`reconcileJoins`, см. главу 1 комментарий) под новый набор источников.
Обратите внимание: `state` не трогается напрямую ни в одной строке — и
`sources`, и сам `state` читаются, но каждое изменение идёт через `setIn`,
которая (из `util.js`, см. главу 2 по соседству) рекурсивно собирает НОВЫЕ
объекты на всём пути `['preset','query','sources']`, оставляя остальные ветки
дерева (`state.dataset`, `state.groupBy`, ...) той же самой ссылкой, что и
была — экономия: не копируется то, что не менялось.

### Композиция — финальный `reducer()`

```js
var domains = [
  presetReducer, entityListReducer, buildReducer,
  groupReducer, tableReducer, sortReducer, quickReducer, advReducer
];
for (var i = 0; i < domains.length; i++) {
  var next = domains[i](state, a);
  if (next !== state) return next;
}
return state;
```

Если действие `a.type` не совпало вообще ни с одним `case` ни в одном домене —
каждый домен по очереди вернёт `state` неизменным (`default: return state;`), и
в итоге сам `reducer()` тоже вернёт `state` как есть — валидный, предсказуемый
"ничего не произошло".

## 5. Rust-трек

Перепишите один `case` на Rust с `enum`+`match` вместо `switch` на строки.
Например, `sort/add`/`sort/remove`/`sort/move`:

```rust
#[derive(Clone)]
struct SortEntry { col: String, dir: Dir }
#[derive(Clone)] enum Dir { Asc, Desc }

enum Action {
    SortAdd,
    SortRemove { index: usize },
    SortMove { index: usize, dir: i32 },
}

fn sort_reducer(sort_by: &[SortEntry], action: &Action) -> Option<Vec<SortEntry>> {
    match action {
        Action::SortAdd => {
            let mut next = sort_by.to_vec();
            next.push(SortEntry { col: String::new(), dir: Dir::Asc });
            Some(next)
        }
        Action::SortRemove { index } => {
            let mut next = sort_by.to_vec();
            next.remove(*index);
            Some(next)
        }
        _ => None,
    }
}
```

Ключевое отличие от JS: `Action` — закрытое множество вариантов, известное
компилятору целиком. Допишите `SortMove` в `match` — если забудете (оставите
`_ => None` как единственный путь), компилятор НЕ заставит вас обработать
каждый вариант, но если вы явно напишете `match` без catch-all `_` и забудете
один вариант `enum Action` — компиляция провалится ("non-exhaustive match").
Попробуйте убрать `_ => None` и посмотреть на ошибку компилятора — это именно
то, чего JS-овский `switch`/`default` никогда не даст.
