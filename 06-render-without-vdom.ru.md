## 1. Теория

### Цена обновления DOM и два ответа на неё

Операции, которые по-настоящему меняют отображённую страницу — вставка или
удаление узла, изменение атрибута, способного повлиять на геометрию, — не
бесплатны: за ними следует раскладка (layout) и перерисовка (paint), и обе
эти стадии стоят заметно дороже, чем выполнение обычного JS-кода, который к
ним привёл. Любой нетривиальный интерфейс, где состояние меняется часто,
вынужден так или иначе отвечать на один и тот же вопрос: как минимизировать
число таких дорогих операций, если сам факт «что-то изменилось» известен
только на уровне «изменилось какое-то состояние», а не на уровне «вот эти
три конкретных DOM-узла».

Подход, получивший широкую известность благодаря React (2013) и
библиотеке `virtual-dom`, вышедшей примерно тогда же, — построить на каждое
изменение состояния не настоящий DOM, а лёгковесное, чисто JS-описание
дерева интерфейса, которое принято называть виртуальным DOM. Такое описание
— обычный JS-объект, создание и сравнение которого почти ничего не стоит по
сравнению с настоящими операциями над браузерным деревом. Библиотека
сравнивает новое описание со старым и вычисляет минимальный набор
реальных изменений — этот узел поменял текст, у этого обновился атрибут,
этот элемент нужно вставить, — а затем применяет к настоящему DOM только их.
Задача «найти минимальный набор операций, превращающих одно дерево в другое»
— классическая алгоритмическая тема (edit distance между деревьями), но её
точное решение дорого само по себе; все практические VDOM-реализации
применяют эвристики, а не точный алгоритм, — например, предполагают, что
узлы одного уровня с совпадающим типом и ключом (`key`) соответствуют друг
другу, не проверяя все возможные перестановки.

`ds-webui` отвечает на тот же вопрос прямо противоположным образом: никакого
промежуточного описания и никакого диффинга вообще. На каждое изменение,
которое должно отразиться на экране, код просто очищает нужный DOM-узел
(`clear()`) и строит его заново через `el()` (главы 2-3). Цена такого решения
симметрична его простоте: диффинг не стоит вообще ничего, потому что его
попросту нет, но и любое изменение — даже затрагивающее одну строку таблицы
из тысяч — обходится так же, как полная перестройка всего узла. Это прямая
причина необходимости главы 9 (батчинг построчного рендера): без диффинга
нельзя «дёшево» обновить одну конкретную строку средствами самого рендера —
обновляются либо все узлы сразу, либо для частного случая приходится
придумывать отдельный, узкий путь в обход основного механизма, которым в
`ds-webui` стал `renderMore`.

### `shellChanged` — ручная, грубая версия диффинга

```js
var shellChanged = state.route !== lastRoute || state.dataset !== lastDataset
  || state.advOpen !== lastAdvOpen || state.exportOpen !== lastExportOpen;
```

Это не диффинг в смысле VDOM (сравнение дерева узел за узлом), а один
грубый булев флаг «поменялось ли хоть что-то из того, что требует
пересборки всей оболочки страницы» — если нет, можно обойтись более узким
обновлением (`root.replaceChild`, см. ниже) или вообще ничего не трогать в
оболочке целиком.

Для поля `dataset` этот флаг обязан отвечать на конкретный вопрос: произошла
ли новая сборка, а не просто «похожая» на предыдущую. Сравнение по ссылке
(`!==`) отвечает на него напрямую и надёжно: `build/success` в `store.js`
всегда создаёт новый объект `dataset`, независимо от того, совпала ли его
форма с прошлым, — поэтому ссылочное неравенство безошибочно означает «была
новая сборка», а равенство — «ничего не изменилось». Любая более слабая
проверка, основанная не на ссылке, а на форме данных (например, на паре
«число колонок + число строк»), рискует дать ложное совпадение: две разные
по существу сборки — с другим срезом `as_of` или другим именем пресета, но
с тем же набором колонок и тем же числом строк — оказались бы для такой
проверки неотличимы, хотя шапка страницы (там же отображаются имя пресета
и срез) обязана показывать именно актуальную сборку. Это та же самая идея,
что уже встречалась в главе 3 при домен-диспетчеризации через `=== state`:
инвариант «любое реальное изменение создаёт новый объект» делает ссылочное
сравнение одновременно самым дёшевым и самым надёжным способом ответить на
вопрос «что-то изменилось?».

## 2. Разбор кода

```js
var render = function (state) {
  var d = store.dispatch;

  document.body.classList.toggle('route-table', state.route === 'table');
  clear(footerNode).appendChild(viewFooter(footerText(state), !state.dataDir));

  if (!state.manifest || !state.preset) {
    clear(root).appendChild(el('p', ..., 'Инициализация…'));
    return;
  }

  if (state.building && !state.dataset) {
    clear(root);
    root.appendChild(viewNav(state, d));
    root.appendChild(el('section', ..., 'Открываю таблицу по пресету по умолчанию…'));
    lastRoute = null; lastDataset = null;
    return;
  }

  var shellChanged = ...; // см. выше

  if (shellChanged || root.children.length < 2) {
    clear(root);
    root.appendChild(viewNav(state, d));
    root.appendChild(
      state.route === 'build' ? viewBuild(state, d)
        : state.route === 'entities' ? viewEntities(state, d)
        : viewTableShell(state, d)
    );
    lastRoute = state.route; lastDataset = state.dataset;
    lastAdvOpen = state.advOpen; lastExportOpen = state.exportOpen;
  } else if (state.route === 'build') {
    root.replaceChild(viewBuild(state, d), root.children[1]);
  } else if (state.route === 'entities') {
    root.replaceChild(viewEntities(state, d), root.children[1]);
  }

  if (state.route === 'table') {
    storage.set('renderWatchdog', true);
    renderExportPanel(state, d); renderAdvFilter(state, d); renderGrid(state, d);
    requestAnimationFrame(function () {
      requestAnimationFrame(function () { storage.set('renderWatchdog', false); });
    });
  } else if (state.buildError) {
    storage.set('renderWatchdog', false);
  }
};
```

Три слоя "дешевизны", от самого грубого к самому точному:
1. Если маршрут/датасет/открытость панелей не менялись — вообще не трогаем
   `root` (ветка `else if route==='build'`/`'entities'` — `root.replaceChild`
   обновляет ТОЛЬКО второй ребёнок — саму страницу, а не навбар рядом).
2. Если что-то из "структурного" изменилось — полный `clear(root)` + заново.
3. Внутри страницы «Таблица» — `viewTableShell` строится полностью только
   когда что-то "структурное" (shellChanged) изменилось; сама таблица
   (`renderGrid`) и обе панели (`renderExportPanel`/`renderAdvFilter`)
   перестраиваются **на любой рендер**, независимо от shellChanged — у них
   свой персистентный `<div id="grid">`/`#advfilter`/`#export-panel"`, который
   `clear()`-ится и строится заново при каждом вызове `render`, пока маршрут —
   «Таблица» (см. комментарий к `viewTableShell`, строка 9-10 файла
   `view-table.js`).

`root.replaceChild(newNode, root.children[1])` — заметьте, не
`clear(root.children[1])`+`append`, а именно замена целого узла: `viewBuild`/
`viewEntities` возвращают НОВЫЙ `<section>` целиком при каждом вызове — старый
просто выбрасывается вместе со всем содержимым.

### Крах-watchdog — побочный, но важный штрих

`storage.set('renderWatchdog', true)` ставится ДО тяжёлого рендера таблицы,
снимается только после ДВУХ вложенных `requestAnimationFrame` — подробно
разберём именно этот механизм в главе 9 (event loop), здесь достаточно
заметить: снятие флага специально отложено за пределы синхронного выполнения
`render()`, потому что реальный краш от нехватки памяти на огромном DOM
обычно случается не в момент исполнения JS, а при последующей раскладке/
отрисовке браузером уже ПОСЛЕ возврата из функции.

## 3. Упражнения (бумага)

**6.1** Почему `state.dataset !== lastDataset` обязана быть сравнением
ССЫЛОК, а не `deepEqual`? Распишите конкретный сценарий (тот самый из
комментария кода): два разных `build/success` с одинаковым числом колонок/
строк, но разным `as_of` — что пошло бы не так при `deepEqual`-сравнении
(подсказка: `as_of` хранится не в `dataset`, а где?). Проверьте себя,
заглянув в `store.js::buildReducer`'s `case 'build/success'`.

**6.2** Распишите по шагам, для каждого `render()` в следующей
последовательности действий, какая ветка (`clear(root)` полностью /
`root.replaceChild` / ни то ни другое) сработает:
1. Старт, `route: 'build'`, датасета нет.
2. Пользователь выбрал источник (`preset/toggleSource`) — датасета всё ещё
   нет, маршрут не поменялся.
3. `build/success` — датасет появился, маршрут автоматически стал `'table'`
   (см. `main.js::buildDataset`, глава 1 его бегло касалась).
4. Пользователь переключил чекбокс "скрыть пустые колонки" (`table/
   toggleHideEmpty`) — маршрут и `dataset`-ссылка не изменились.

**6.3** `renderGrid`/`renderAdvFilter`/`renderExportPanel` перестраиваются
ПОЛНОСТЬЮ на каждый `render()`, пока маршрут — «Таблица», независимо от
`shellChanged`. Почему это разумно для `renderAdvFilter`/`renderExportPanel`
(относительно маленькие панели), но именно для `renderGrid` (потенциально
тысячи строк) стало проблемой, решённой отдельно, батчингом (глава 9)?

## 4. Упражнения в DevTools

**6.4 — DOM breakpoint на подмену поддерева.** В Elements выберите
`<div id="grid">`, правый клик → **Break on → Subtree modifications**.
Кликните по любой пиктограмме сортировки в заголовке столбца. Исполнение
должно остановиться — откройте **Call Stack**: найдите в нём `clear`,
вызванный изнутри `renderGrid`. Снимите точку останова (или продолжите
исполнение несколько раз подряд, Resume) и обратите внимание, сколько раз
брейкпоинт срабатывает за один клик (каждый `removeChild` внутри `clear()` —
отдельное "subtree modification").

**6.5 — то же на `#app`.** Повторите для `<div id="app">` (а не `#grid`) —
переключитесь между «Конструктором»/«Индикаторами»/«Таблицей» через навбар.
Сравните: когда срабатывает брейкпоинт чаще — при переключении МАРШРУТА
(shellChanged=true, полный `clear(root)`) или при правке чекбокса на
«Таблице» (shellChanged=false, `root` вообще не трогается — подтвердите, что
в этом случае брейкпоинт на `#app` НЕ сработает вовсе, хотя на `#grid`
сработает).

**6.6 — Performance, первая ориентировка (не глубокий профиль — это глава
9).** Запишите короткую сессию Performance: один клик по пиктограмме
сортировки на таблице с сотней-другой строк. Остановите запись, найдите на
временной шкале сегмент жёлтого цвета (**Scripting**) — это и есть
исполнение `render()`→`renderGrid()`. Отдельно — найдите фиолетовый
(**Rendering**)/зелёный (**Painting**) сегмент сразу после него — это то, что
браузер делает ПОСЛЕ вашего JS, раскладка и отрисовка нового DOM.

## 5. Rust-трек

DOM специфичен для браузера, но сама ЗАДАЧА диффинга — нет. Мини-упражнение:
напишите на Rust игрушечный "дифф" для простого дерева:

```rust
enum Tree { Leaf(String), Node(String, Vec<Tree>) }

enum Patch { Replace(Tree), UpdateText(String), NoOp }

fn diff(old: &Tree, new: &Tree) -> Patch {
    match (old, new) {
        (Tree::Leaf(a), Tree::Leaf(b)) if a == b => Patch::NoOp,
        (Tree::Leaf(_), Tree::Leaf(b)) => Patch::UpdateText(b.clone()),
        _ => Patch::Replace(new.clone()),   // упрощённо: разная структура -> просто заменить целиком
    }
}
```

Это ИМЕННО та работа, которую `ds-webui` сознательно не делает (`clear()`+
rebuild вместо diff+patch) — задание: расширьте `diff`, чтобы для двух
`Node`-узлов с ОДИНАКОВЫМ тегом она рекурсивно диффила детей по позиции
(вместо `Patch::Replace` на любое отличие) — почувствуете, сколько случаев
нужно аккуратно обработать (разное число детей? переставленные дети?) даже
в игрушечной версии — и поймёте, почему `ds-webui`, учитывая его масштаб,
осознанно выбрал не делать этого вовсе.
