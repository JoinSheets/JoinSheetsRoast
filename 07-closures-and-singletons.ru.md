## 1. Теория

### Замыкание: определение и минимальный пример

Глава 1 уже вводила общее определение: замыкание — это функция вместе с
захваченной ею областью видимости, той, в которой она была создана (на
примере IIFE и инкапсуляции в `ds-webui`). Здесь стоит закрепить это
определение отдельным, предельно изолированным примером, прежде чем
переходить к более тонкому эффекту, который понадобится для разбора кода
ниже:

```js
function makeCounter() {
  var count = 0;              // переменная внешней функции
  return function () {        // внутренняя функция — "помнит" count
    count += 1;
    return count;
  };
}
var c1 = makeCounter();
c1(); // 1
c1(); // 2 — count не сбросился между вызовами, хотя makeCounter() давно вернула результат
var c2 = makeCounter();
c2(); // 1 — у c2 своя собственная, отдельная count
```

Важная деталь: `c1` и `c2` — разные замыкания, каждое со своей копией
`count`, потому что каждый вызов `makeCounter()` создаёт новую область
видимости. Код `view-table.js` работает иначе: вся его IIFE выполняется
ровно один раз, при загрузке файла (см. главу 1), и все функции, определённые
внутри неё, делят одну и ту же, единственную копию переменных, объявленных
на верхнем уровне этой IIFE — ближе к тому, как если бы `makeCounter()` была
вызвана всего однажды на всё приложение.

### Модульный синглтон

Приём, возникающий из этого единственного вызова IIFE, в JavaScript-
сообществе получил собственное имя задолго до того, как в язык добавили
настоящие модули, — module pattern, которое Дуглас Крокфорд описал в начале
2000-х и которое затем вошло во все каталоги JS-паттернов того времени:

```js
(function () {
  var quickDraft = {};   // "модульная переменная" — видна всем функциям ниже, невидима снаружи
  var renderGrid = function (state, d) { ... quickDraft ... };
  ...
})();
```

Снаружи файла до `quickDraft` нет доступа вообще — IIFE её не экспортирует.
Это и называют модульным синглтоном: ровно один экземпляр состояния на весь
файл, общий для всех функций внутри, недостижимый снаружи. В языке с
настоящей модульной системой (Rust, Python, современный ESM) та же идея
выражается явным, встроенным в язык средством — ключевым словом `pub` или
его отсутствием, конвенцией `_`-префикса, самой модульной областью видимости
— в файле `view-table.js` она достигается исключительно через замыкание
вокруг общей IIFE, потому что никакого другого средства инкапсуляции здесь,
как было показано в главе 1, в принципе нет.

### Замыкание держит переменную, а не значение

Самая частая ошибка при первом знакомстве с замыканиями — считать, что
замыкание «снимает копию» значения в момент создания функции. В
действительности оно держит ссылку на саму переменную, на ту же ячейку
памяти, и если эта переменная меняется после создания функции, замыкание
увидит именно новое значение, а не то, что было зафиксировано когда-то
раньше:

```js
var x = 1;
var readX = function () { return x; };
x = 2;
readX();   // 2, не 1 — readX замкнута на переменную x, не на значение 1
```

Этот эффект — не побочная тонкость, а ровно тот механизм, на котором строится
пара `currentState`/`currentDispatch`, разбираемая в коде ниже.

## 2. Разбор кода

```js
var quickDraft = {};
var searchCursor = {};
var ROW_RENDER_BATCH = 1000;
var pendingFocus = null;
var docCloseListenerAttached = false;
var currentState = null, currentDispatch = null;
var currentEnsureMemberRendered = null;

var attachDocCloseListener = function () {
  if (docCloseListenerAttached) return;
  docCloseListenerAttached = true;
  document.addEventListener('click', function (e) {
    var t = e.target;
    if (t && t.closest && (t.closest('.quick-panel') || t.closest('.col-icon'))) return;
    var qo = currentState && currentState.quickOpen;
    if (!qo || !Object.keys(qo).some(function (k) { return qo[k]; })) return;
    if (currentDispatch) currentDispatch({ type: 'quick/closeAll' });
  }, true);
};

var renderGrid = function (state, d) {
  ...
  currentState = state;
  currentDispatch = d;
  attachDocCloseListener();
  ...
};
```

Семь ролей, семь переменных:
- `quickDraft`/`searchCursor`/`pendingFocus` — черновики ввода quick-панелей
  (поиск/фильтр), намеренно НЕ в `store.js`'s состоянии — это сознательное
  решение (комментарий строк 290-292): они "эфемерные", живут только пока
  открыта страница, не должны попадать в историю действий/пресет.
- `docCloseListenerAttached` — классический guard "навесить слушатель ровно
  один раз". Без него `attachDocCloseListener()`, вызываемая на КАЖДЫЙ
  `renderGrid` (а значит на каждый клик/dispatch вообще, пока открыта
  «Таблица»), навесила бы ещё один `document.addEventListener('click', ...)`
  при каждом рендере — через сотню действий пользователя на странице
  накопилась бы сотня идентичных слушателей, каждый из которых отработал бы
  на следующий клик (не катастрофа функционально — `quick/closeAll` идемпотентен
  — но чистая утечка памяти и лишняя работа на каждый клик).
- `currentState`/`currentDispatch` — САМОЕ важное для понимания замыканий
  здесь. `document.addEventListener('click', function (e) {...})` вызывается
  **один раз** (guard выше), значит, сама функция-обработчик создаётся **один
  раз** и живёт всё время, пока страница открыта. Но ей нужно реагировать
  на АКТУАЛЬНОЕ состояние — на момент клика, не на момент, когда её
  регистрировали. Если бы код выглядел так:
  ```js
  var attachDocCloseListener = function (state, d) {   // гипотетически
    document.addEventListener('click', function (e) {
      if (d) d({ type: 'quick/closeAll' });   // замкнулось на ПЕРВЫЕ state/d навсегда
    }, true);
  };
  ```
  — обработчик замкнулся бы на конкретные значения `state`/`d`, переданные в
  момент ПЕРВОГО вызова, и дальше, после первого `dispatch`, они стали бы
  устаревшими (`stale closure`) — обработчик продолжал бы диспетчить в
  старый, давно не актуальный `d`, а проверял бы давно не актуальный `state.
  quickOpen`. Решение в реальном коде — замкнуться не на ЗНАЧЕНИЯ `state`/`d`
  напрямую, а на МОДУЛЬНЫЕ переменные `currentState`/`currentDispatch`, которые
  переприсваиваются (`currentState = state; currentDispatch = d;`) на каждый
  `renderGrid` — и единственный, живущий вечно, слушатель каждый раз читает
  их АКТУАЛЬНОЕ, самое свежее значение в момент клика.
- `currentEnsureMemberRendered` — отличается от `currentState`/`currentDispatch`
  тем, что переприсваивается не просто НОВЫМ значением той же формы, а
  **совершенно новой функцией** на каждый `renderGrid` (строка 685):
  ```js
  currentEnsureMemberRendered = function (ridx) {
    for (var i = renderedCount; i < rowDescriptors.length; i++) { ... }
  };
  ```
  Потому что эта функция сама замыкается на `renderedCount`/`rowDescriptors`/
  `materializeRow` — ЛОКАЛЬНЫЕ переменные ВНУТРИ конкретного вызова
  `renderGrid`, которые создаются заново при каждом вызове и не существуют
  как общие "модульные" переменные (в отличие от `currentState`). Их нельзя
  "обновить на месте" — можно только заменить всю функцию, которая их
  держит, целиком.

## 4. Упражнения в DevTools

**7.4 — Scope panel, увидеть замыкание буквально.** В Sources поставьте
брейкпоинт внутри обработчика клика — строка `if (currentDispatch)
currentDispatch(...)`. Кликните где-нибудь на странице «Таблица» (вне
quick-панели, с открытой любой quick-панелью, чтобы брейкпоинт сработал — иначе
функция рано вернётся на строке с `if (!qo...)`). Когда исполнение
остановится — в панели **Scope** найдите раздел **Closure (attachDocCloseListener)** —
там должны быть видны `currentState`/`currentDispatch` как захваченные
переменные. Это прямое, визуальное подтверждение того, что замыкание
"держит" именно эти конкретные переменные.

**7.5 — попытка достать приватное снаружи.** В Console наберите
`typeof window.quickDraft` и `typeof DS_APP.quickDraft` — оба должны дать
`"undefined"`. Это эмпирическое доказательство того, что IIFE+замыкание дают
НАСТОЯЩУЮ приватность, не просто "соглашение об именовании" — снаружи файла
к `quickDraft` в принципе нет пути, в отличие, например, от `_entityColumns`
(до переименования в прошлой сессии) — тот был технически доступен, просто
по конвенции "не трогать".

**7.6 — посчитать слушателей.** В Console выполните
`getEventListeners(document).click` (Chrome-only утилита) — должен быть
РОВНО один `click`-слушатель с `useCapture: true` (это и есть
`attachDocCloseListener`'s слушатель). Переключитесь на страницу «Таблица»
туда-обратно несколько раз (покидая и возвращаясь) — пересчитайте список
снова: он не должен расти, несмотря на то, что `renderGrid` вызывался много
раз — живое подтверждение работы guard'а из упражнения 7.1.

## 5. Rust-трек

Замыкания есть и в Rust (`Fn`/`FnMut`/`FnOnce`), но правила владения делают
паттерн "один долгоживущий замкнутый обработчик + модульная мутируемая
переменная, которую кто-то ещё переприсваивает снаружи" — то, что мы только
что разобрали — НЕ тривиальным, а местами невозможным без явных
дополнительных конструкций:

```rust
use std::cell::RefCell;
use std::rc::Rc;

struct AppState { quick_open: bool }

fn main() {
    let current_state: Rc<RefCell<Option<AppState>>> = Rc::new(RefCell::new(None));
    let captured = Rc::clone(&current_state);
    let on_click = move || {
        if let Some(state) = captured.borrow().as_ref() {
            println!("quick_open = {}", state.quick_open);
        }
    };
    // где-то ещё, "на каждый renderGrid":
    *current_state.borrow_mut() = Some(AppState { quick_open: true });
    on_click();
}
```

Задание: объясните (письменно, себе), зачем здесь понадобились СРАЗУ ДВА
дополнительных типа — `Rc` (разделяемое владение: и `on_click`, и код снаружи
должны иметь доступ к ОДНОЙ и той же ячейке) и `RefCell` (разрешает менять
значение изнутри, даже когда формально есть несколько "владельцев" через
`Rc`) — там, где JS не просил вообще ничего, кроме обычной `var`. Это и есть
ответ на вопрос "что даётся легко в JS, но требует explicit-решения в Rust" —
компилятор Rust НЕ ПОЗВОЛИЛ БЫ вам просклеить "один замкнутый на переменную
обработчик" + "кто-то снаружи её меняет" без явного указания, кому
принадлежит переменная и как разрешена мутация — ценой чуть большего
количества кода вы получаете гарантию, что нет двух одновременных мутаторов,
которые могли бы испортить друг друга (data race) — гарантия, которой JS в
принципе не даёт и не может дать.
